    Protocol flow

    How a swap settles on Zenon

    Nostr carries the order and the private coordination. One hash links both HTLCs: the maker locks the base leg, the taker verifies it and locks the quote leg with the same hash, and the unlock that takes the quote leg publishes the preimage the maker's counterparty needs.

    Sequence diagram: Alice publishes an order through Nostr; Carol reserves it; Alice creates the base HTLC on Zenon; Carol verifies it on chain and creates the quote HTLC with the same hash; Alice unlocks the quote HTLC, which reveals the preimage; Carol reads the preimage from the chain and unlocks the base HTLC.

    Three private messages Open the settlement handshake

    zwap's settlement flow uses three authenticated DMs. After the third message both wallets advance from independently verified chain state — no private acknowledgement is trusted.

    1. 01

      Taker → maker order key

      reserve_propose

      Requests this exact order and fill amount. It binds the current public projection, the trade terms, and the taker's fresh session and Zenon settlement addresses.

    2. 02

      Maker order key → taker session

      reserve_accept

      Publishes the reserved projection and names the base-side HTLC on chain. The hashlock, the expiration height, the token standard, and the amount are signed together.

    3. 03

      Taker session → maker session

      quote_lock

      After verifying the first HTLC against the chain, the taker creates the quote HTLC with the same hashlock and a shorter expiration. This is the final private message.

    After quote_lock

    The maker unlocks the quote HTLC, which writes the preimage into the chain. The taker reads that preimage and unlocks the base HTLC. The maker then publishes the signed fill projection; the taker verifies it. If either side stalls, the expiration lets each creator reclaim their own leg.

    What matters

    Know the trust boundary.

    01

    Trust the chain, not the peer.

    A private message is coordination, not proof. Verified HTLC state and the on-chain preimage decide whether a leg actually settled.

    02

    Ephemeral keys, no ceremony.

    Every reservation gets fresh Nostr session keys. zwap scopes and stores them for the swap; you never manage a key ceremony.

    03

    Nostr coordinates. It does not custody.

    Relays carry orders and encrypted coordination. Preimages, seeds, and private keys stay out of public events.

    04

    Atomic under Zenon's HTLC rules.

    One hash links both legs and staggered expiration heights provide recovery. Safety depends on the Network of Momentum enforcing the embedded HTLC contract.

    05

    Plasma, not fees.

    Zenon is feeless. Sends need plasma from fused QSR, or a proof of work this page computes locally in a worker.

    06

    All local, no servers.

    Your wallet and session state run in this browser. zwap has no account, matching, or custody server; Nostr relays and a Zenon node are the only external infrastructure.
